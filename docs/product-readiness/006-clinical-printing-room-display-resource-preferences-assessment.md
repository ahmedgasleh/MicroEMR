### 2. Root cause and calendar semantics

**Primary classification B:** assignment is supported by persistence/detail retrieval but omitted from the calendar list read model. **Also a primary-only rendering limitation (D in implementation terms):** the event adapter maps only PrimaryResourceUid. Source does not establish that this was an intentional owner/product decision. It is not classification C alone: the room does not reach the ordinary event payload at all.

The code supports room/resource schedule columns and separate blocked-time events, not a dedicated calculated room-availability display. Availability search already considers assigned rooms (`SchedulingReadRepository.GetAvailabilityBusyPeriodsAsync`); a visually empty calendar room column is not evidence that the room is available or that persistence lost the assignment. Unselected rooms or a nonmatching resource-type filter can independently hide a column.

The bundled [DayPilot Lite](../../src/MicroEMR.Web/wwwroot/lib/daypilot/daypilot-javascript.min.js) identifies version 2026.2.839-lite. The application uses `DayPilot.Calendar` Resources view and scalar event resource IDs; the bundle's Event.resource accessor reads/writes `data.resource`. There is no multi-resource binding in the inspected integration. Do not assume a FullCalendar-style resourceIds array, a paid scheduler feature, or native simultaneous columns for one event. One database appointment may have physician and room; the current single event representation cannot display both assignments simultaneously. Separate display projections are compatible with the observed scalar model, subject to focused implementation testing.

Persistence conclusions are **source-supported**, not verification of the owner's exact observed appointment or deployed database. No live appointment was queried in this assessment.

### 3. Smallest correction and expected behavior

Extend the existing list SELECT with a left join from RoomResourceId to ScheduleResource and nullable RoomResourceUid/RoomResourceName; map through Application DTO, Web DTO and Events. No schema, write procedure, relationship or appointment-policy change is needed. Infrastructure currently executes the list SELECT directly, so this is a repository read change, not a new migration.

Render a physician projection and, when assigned, a room projection for the same appointment. Give display projections distinct view IDs and retain the single original AppointmentUid explicitly for every details/edit/status action. A room-only selection must show the room projection even when the physician column is hidden. Do not replace the physician assignment with the room UID, create a second appointment, or fetch details once per event to compensate for the list omission.

For the first correction, keep room projections non-draggable; preserve current provider-to-provider movement and room assignment. Audit the handlers that currently derive identity from event IDs, selection restoration and patient-display rendering. Existing `onEventMoved` explicitly rejects non-Provider destinations near line 1335. Reusing that code unchanged with synthetic IDs could send an invalid appointment ID or misinterpret a room drag as a provider reassignment. Keep blocked events distinct and nonmovable.

**Affected components:** Infrastructure list query/mapping, Application/Web list DTOs, Web Events adapter, calendar projection/filter/interaction code (prefer focused TypeScript for new client logic), relevant focused tests. **UI-only sufficient: NO** for the recommended complete fix; **database/schema migration: NO**. A details-modal-only room label already exists and would not solve room occupancy display.
