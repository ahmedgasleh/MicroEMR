## 4. Minimum implementation design

**Recommend Step 104 implement only Past Medical and Surgical History field completion (Step 101 G2), including its date representation and affected CPP output.** It has one existing owner/table/editor, established concurrent/archived/audited procedures, and no need to touch completed medication, Family or Risk behavior. This is one category with two existing record kinds, not five unrelated domain changes.

Proposed additive contract on `PatientClinicalHistory`:

- Keep HistoryUid, PatientUid, HistoryType, Description, RelevantDate, Status, actors and RowVersion. Description remains the existing diagnosis/problem or procedure text; no coding system or duplicate text field is required by the reused mapping.
- Add nullable medical OnsetDate parts, ClinicalResolutionDate parts, LifeStageCode, ClinicalProblemStatus and Notes; add nullable surgical ProcedureDate parts. Notes applies to both kinds. Use explicit clinical status values Active/Resolved for the minimum supported medical states, with NULL meaning not recorded; this vocabulary is an engineering minimum, not a newly asserted dictionary code set.
- On new/edit forms, Medical exposes onset/stage/resolution/clinical status/notes; Surgical exposes procedure date/notes. Do not require irrelevant fields. Do not infer resolution status from a date. Reject contradictory explicit clinical states (for example explicitly Active with an asserted resolution) without guessing a correction.
- Legacy generic RelevantDate remains visibly labelled as such and retained in responses/print. No automatic Medical-onset/Surgical-procedure reinterpretation. A clinician can explicitly reconcile an old date through an audited, version-protected edit. Changing kind must not silently clear previously stored fields; require deliberate reconciliation or retain them read-only as prior-kind content.
- Add a new tenant migration via the existing manifest runner, choosing the actual next ID at implementation time. Do not edit 0041 or migration history. Extend existing List/Get/Create/Update/Archive projections/audit JSON. No new table or EF migration.
- Keep archived history immutable under the existing contract, retrievable through Archived/All; never force reactivation or bulk rewrite to populate new fields. Historical corrections outside allowed edits require a separately designed workflow, not relaxed terminal-state checks.

A small Application date validation/formatting helper may be introduced for this category, with tests, then reused by later categories. No broad framework or conversion of completed domains is needed.

## 6. Clinical data semantics

- **Unknown:** SQL NULL is unrecorded; blank UI normalizes to NULL and displays Not recorded. No automatic NKA, no-conditions, refused=false, resolved, compliant, Adult or negative family/risk finding. Keep existing explicit allergy-NKA contradiction/replacement/revocation semantics.
- **Dates:** Proposed precision contract uses nullable Year/Month/Day parts: all NULL = unknown; year only = YYYY; year/month = YYYY-MM; all parts = real YYYY-MM-DD. Reject day without month/year, month without year, invalid dates and unsupported precision. SQL nullable SMALLINT/TINYINT parts with CHECK constraints avoid synthetic first-of-month storage. If an existing exact DATE remains, expose it as Day precision without rewriting the row; do not create two writable conflicting authorities.
- **Input compatibility:** For categories retaining an old date field, old exact-date requests remain exact and new partial requests are explicit; conflicting legacy and parts input is rejected. Distinguish omitted new fields from explicit clear on update so old clients cannot erase new clinical content. Implement presence-aware mapping or a versioned save contract; do not rely on nullable defaults to distinguish them.
- **Optional values:** Supported mandatory dates may be unknown on a patient record. Optional Family/Risk/Alert dates remain outside this scope. Keep existing clinic-administered immunization safeguards; historical uncertain dates and refusals need an appropriate distinct path rather than fictitious administration dates.
- **Chronology:** Compare date intervals, not padded dates. Reject a resolution unambiguously before onset; overlapping partial intervals do not prove a contradiction. Preserve existing future-date rules where applicable; use known intervals to detect definitely future partial values, without inferring the actual day. Never timezone-shift clinical date parts. Server audit timestamps remain UTC instants.
- **Life stage:** Reuse `Core/Domain/FamilyHistoryLifeStages.cs` unchanged, as Risk already does: N New born, I Infant, C Child, T Adolescent, A Adult; NULL Not recorded. Validate case-sensitive allowed codes in Application and SQL. Record stage at the relevant clinical event; do not calculate it from current age, DOB, text, onset date or archive time. Do not add an invented U code.
- **Legacy/history:** No bulk UPDATE, coercion of RelevantDate, clinical-status backfill or change to existing RowVersion during upgrade. Preserve all existing clinical text, dates, resolution/archive provenance and audit entries. Audit subsequent intentional changes with old/new precision and values. Retained rows stay retrievable under existing permissions, not physically deleted.

User-supplied actor/tenant identifiers are not trusted.
