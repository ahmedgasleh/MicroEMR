Step 185's retained page text was reused; no PDF/source recovery was repeated.

Requirement column:

> The EMR Offering MUST provide the ability to record patient prescriptions using a publicly available COTS (commercial off-the-shelf) drug database with Canadian drug codes.

The guideline explicitly requires use of COTS, at minimum, for **Drug Name; Drug Strength / Drug Strength UM; Drug Form**. Its page-17 continuation states:

> The EMR Offering MUST use a commercially licensed, COTS drug database, that provides:

It then requires **Health Canada-authorized drug information (e.g., DINs, approved products), clear licensing terms/accountability, and regular updates, maintenance and technical support**. Open-source drug databases lacking those assurances are not accepted. “Publicly available” therefore does not mean a free, unaudited local list or an assumed right to reuse a public endpoint.

**Explicit PC04.01 capabilities:** a real prescription-recording path using the designated Canadian coded COTS source; the minimum source-backed fields above; and evidence that the source meets the stated commercial/support/update assurances. Structural fields, manually entered codes, a mocked provider or native free-form prescribing alone cannot prove that path. The CDS-S medication/prescription reference remains applicable; exact field ownership/provenance mapping must preserve its existing accepted scope.

**Related requirements inform the contract without expanding this task:** PC04.14, page 21, requires an ordinary EMR user to access actual COTS name/last-update information within the application; version number is optional. PC04.15 on that page states that the EMR vendor must update to the most recent COTS version **within two months of release**, covering hosted/on-premises operation, with customer notification/provision for on-site updates accepted. The two-month limit is attributed to **PC04.15**, not invented as PC04.01 wording. No PC04.14/.15 implementation/status or inventory reassessment occurs here. PC04.06/.07/.09 safety/severity/override/threshold obligations remain separate; a catalogue licence is not proof that safety knowledge or those capabilities are included.

## 5. Proposed architecture and pre-vendor adapter decision

**Proposed, not implemented:** a minimal Application-owned catalogue query/selection contract and source-neutral DTOs, with a vendor-specific Infrastructure implementation registered through existing DI. Keep thin authenticated API/Web endpoints, normal TypeScript/Bootstrap form integration, and existing prescription Application orchestration/repository mutation boundaries. Do not add Entity Framework migrations or direct controller SQL writes. Any necessary clinical persistence change must use the established stored-procedure/audit pattern after its exact source/provenance needs are approved.

The boundary should distinguish a source-qualified product identity, human-readable name/strength/form, relevant ingredient/route/status information when actually supplied, source release/provenance and explicit outcomes (match/no match/unavailable/unauthorized/unsupported). It must not assume all suppliers have the same identifier cardinality, route vocabulary, generic grouping, units or transport. A UI selection is a candidate; the server must enforce the approved product/release/context contract before treating it as source-backed prescription content. Historical prescriptions must remain readable after catalogue updates without being rewritten.

Existing Web→API HttpClient/DTO/cancellation patterns are reusable. Supplier authentication belongs in Infrastructure/server configuration with separate credentials/entitlements; no API user bearer forwarding. Avoid broad new retry/caching/framework dependencies: adopt only behavior permitted by the contract and required by the specific source. Catalogue search/retry must never automatically retry a clinical prescription save.

**Can an adapter be implemented safely before vendor selection? CONDITIONAL, narrowly.** After separate authorization, a minimal transport-independent port/DTO scaffold with isolated test doubles and no production source registration, clinical saves, new database or certification claim could be reversible engineering preparation. This would not validate an actual integration. Concrete source parsers, identity mapping, caching/redistribution, update ingestion, production UI activation and persistence design are **not ready** without real schema/licence/semantic inputs. Do not harden a placeholder dataset into an assumed vendor contract. The smallest useful next step is the source decision, so this report recommends **deferring adapter implementation**, not speculative scaffolding now.

Tenant isolation remains mandatory even if a licensed reference catalogue may eventually be shared: keep tenant/patient prescriptions and clinical audit in the selected tenant database, enforce source entitlements and tenant-specific overlays independently, and never share patient-context search/history caches between tenants. Share only reference content that the licence permits. No patient identifier, private note or unrestricted free-text clinical query should be sent to a supplier without a separately approved necessary data-flow contract.
