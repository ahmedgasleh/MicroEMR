## 6. Confirmed gap and smallest proposed solution

**Step 127M finding E: multiple independently verified limitations.** Request-to-audit propagation is already present; explanations A/B/C (missing request propagation, per-operation generated correlations, or request IDs absent from audit storage) are not supported for these paths. Verified limitations are:

1. When Activity exists, the custom completion event lacks the HTTP request ID already stored in the clinical audit. A trace ID alone is a different, potentially shared identifier.
2. Successful custom completion events are Debug, below the checked-in Information defaults; no effective successful-request capture was obtained in 127L.
3. Audit rows contain no endpoint/status mapping, and the preserved browser observations/current server evidence do not supply one. This is partly an evidence-capture limitation; it is not evidence of incorrect audit insertion or insufficient SQL timestamp precision.

The absence of route metadata in AuditLog need not be corrected in the schema: a sanitized operational completion event can supply the mapping. **Smallest recommended implementation, separately authorized:** add a distinct structured RequestId property to the existing shared SafeOperationalLog.RequestCompleted event using the already-supplied fallbackTraceIdentifier argument, preserving existing TraceId/SpanId selection and all clinical audit calls/values. Both middleware callers already provide the required HTTP ID; no new middleware, request-context abstraction, DTO, header or dependency is required. Capture service/process-instance context operationally when joining logs, since opaque IDs should not be treated as globally unique forever.

Separately arrange bounded Debug capture for the existing API/Web telemetry logger categories under reviewed diagnostic configuration; changing the event payload alone will not make suppressed successes visible. Avoid blanket HttpClient/framework logging or unrestricted scope/header dumps, which can expose raw paths/queries. This recommendation is a small observability change, not a new clinical-audit requirement. A configuration/provider-only alternative is viable only if it can already produce the same sanitized request-ID/route/status mapping; that capability is not established by this evidence.

With that bridge, join API RequestId to AuditLog.RequestCorrelationId, keeping Activity TraceId/SpanId as separate fields for Web-to-API grouping. One navigation can involve multiple traces, notably a separate browser XHR; a shared distributed trace is not a mandatory replacement navigation ID. No change to stored procedures/schema, past rows, event frequency, existing field meaning or audit success boundary is necessary. Do not repurpose NewValue, EntityId or ActionName for tracing. Switching the stored correlation to Activity.TraceId could group multiple requests, break diagnostic/query consumers and alter existing records' interpretation; do not do it. Consumer compatibility outside the inspected paths has not been exhaustively inventoried, which strengthens the case for leaving persistence untouched.
