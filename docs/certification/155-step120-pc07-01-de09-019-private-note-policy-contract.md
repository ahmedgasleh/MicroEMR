## 5. Permission and audience contract

Existing Patients.View alone is **insufficient**: it authorizes ordinary charts, without distinguishing prescription staff. Patients.View + Prescriptions.Prescribe identifies prescribers but cannot represent approved nonprescribing clinical readers. Do not silently equate either with the approved audience.

Smallest authorization addition: **`Prescriptions.ViewPrivateNotes`**, a clinical prescription-detail read capability. Read requires **Patients.View AND Prescriptions.ViewPrivateNotes**, authenticated subject, Active selected-tenant membership and active resolved clinical user. Only designated clinical staff receive it through the existing access-profile/override machinery. No automatic grant to all chart readers, all prescribers, administrators or support accounts; no new clinical role taxonomy. Tenant administrators assign it explicitly to approved clinical staff. That operational assignment is a deployment prerequisite, not an unresolved clinical policy or evidence of a grant today. Existing explicit denies win under existing effective-permission rules.

Write requires both read permissions plus **Prescriptions.Prescribe**, active mapped Provider and `actor.UserId == parent.PrescriberUserId`, with parent Draft and reviewed current version. No separate write permission is necessary: the existing prescribe permission plus stricter ownership/status gate expresses the approved writer. A prescriber without the new read capability may continue ordinary prescribing with the private field omitted; cannot create/edit/clear it. Explicit private input without field authorization rejects the whole request, even null/blank; never silently discard it or save other fields partially.

Resolve reads through IAuthenticatedClinicalUserAccessor before protected fetch; writes use ClinicalUserActorContext supplied by middleware and Application-level checks for noncontroller callers. Do not accept posted PrescriberUserId, ProviderUid, author label, CreatedBy, user claim containing a numeric clinical ID or client CanEdit as proof. SQL rechecks active user/provider, compound ownership, Draft and version within mutation transaction. Missing/inactive user rejects; inactive/unmapped Provider prevents writes using established mapping failure semantics. Historical reads do not require the original author's Provider to remain active; the current reader must be active and entitled.

Selected tenant comes exclusively from trusted context and verified tenant connection. Resolve live patient and parent matching **both PatientUid and PrescriptionUid** before protected data load/success audit. Row association must enforce matching patient, not just an unconstrained note UID. Foreign/missing resources return the existing non-disclosing 404/403 convention; responses never disclose another patient's identity or note existence. Invalid tenant membership rejects before tenant clinical access. No privileged database-access claim is made by these application permissions.

## 6. Lifecycle, original prescriber and correction contract

**Original prescriber means immutable PatientPrescription.PrescriberUserId for the specific order owning the note.** At creation current trusted actor becomes that identity. PrescriberProviderUid and name/credential snapshots provide attribution, not an interchangeable author credential. Provider remapping does not transfer authorship; no delegated author, reassignment or inactive-author bypass.

Current corrections are new prescriptions attributed to their creating clinician. The original source prescriber can create/edit a correction through the existing workflow when active and permitted. Another authorized prescriber can also create a correction today; that clinician is the original prescriber of the **new** draft, and may independently enter its new note if entitled. This does not authorize reading or editing the source note. Requiring the source prescriber to own every later correction would change existing workflow and is not imposed. No conflict remains with the approved per-prescription rule; a future demand for source-author-only correction ownership would be **BLOCKED — DESIGN CONFLICT**, requiring a specific decision to restrict existing correction authorship before implementation.

| Event | Required result |
| --- | --- |
| Create Draft | Optional independent note entered by its trusted original prescriber; omitted/null/blank starts no note. If nonempty, commit parent, note, initial protected revision and required audits together. |
| Update Draft | Original prescriber and full field authorization; present text replaces, present null/whitespace clears, omission preserves. Review parent RowVersion. Another clinician never edits even if able to read. |
| Finalize or sign-and-finalize | Acquire same parent update lock as note writers; verify current version and change Draft to Finalized atomically. No pending note autosave; user saves note first. Preserve content and revision history. Private note is not covered by the outward artifact signature. |
| After finalization | Reject explicit note update/clear, even if value is unchanged. Cancelled/Superseded also reject. No silent replacement, resurrection as Draft or post-finalization note amendment. |
| Cancellation | Existing cancellation is Finalized-only; retain note and history unchanged. No new draft-abandon/delete workflow. |
| Correction creation | New linked draft has no protected note row/content; correction API fetches only public source contract and copies no note or revision. Creation response has no source note. Independently entered destination note needs its own author/permissions/version. |
| Supersession | Source note remains on source; new record's independent note stays on new record. No propagation through service/SQL/DTO/snapshot. |
| Historical views | Authorized protected detail remains readable for Finalized/Cancelled/Superseded, including inactive original prescriber; current reader checks and read audit still apply. |
| Existing records | No fabricated notes, no field backfill. Existing finalized records stay absent and cannot acquire a new note. Existing drafts may acquire one only through an authorized owner action. Existing artifacts stay unchanged. |

## 7. Recommended protected persistence and concurrency

Choose **a tenant-local one-to-zero/one protected note table plus append-only protected revisions**, associated with PatientPrescription; use the **parent's existing RowVersion**, with no independently reviewed note RowVersion. This is smaller and safer than independent concurrency/lifecycle tokens and avoids full-row parent audit disclosure.

Proposed `dbo.PatientPrescriptionPrivateNote`: internal identity key, unique PrivateNoteUid, unique PrescriptionUid, PatientUid, OriginalPrescriberUserId, nullable NoteText `nvarchar(1000)`, CreatedBy/CreatedAtUtc, UpdatedBy/UpdatedAtUtc and current RevisionNumber. Parent is authority for status, prescriber and reviewed token; do not duplicate mutable lifecycle state. Tenant ownership is inherited from the verified tenant-clinical database, matching existing conventions; no client-selected TenantUid or redundant cross-store foreign key. Enforce composite parent/patient association (unique parent pair plus FK where needed) and original-author consistency in procedures. No cascading deletes.

The **1,000 UTF-16 code-unit** plain-text bound is an engineering choice aligned with existing prescription free text, not an OntarioMD limit. Trim surrounding whitespace; null/blank means not recorded. Preserve internal line breaks; HTML-encode rendering, no rich text. Validate raw length before narrowing in API/Application/Infrastructure/SQL; `nvarchar(max)` procedure input avoids silent truncation. No operational logging of rejected values.

No row means never recorded/legacy unknown. Once a nonempty note exists, explicit clear keeps the same record/UID with NoteText NULL and a new clear revision; never delete it. Entitled detail can show Not recorded for both states; broad DTOs have no presence flags. Initial explicit blank/null is allowed and audited as an explicit clear attempt without fabricating prior content; it need not create a note row. Omitted create has no note event. Repeated authorized explicit writes are audited as such, including an unchanged value, without pretending a content difference occurred.

Proposed `dbo.PatientPrescriptionPrivateNoteRevision`: unique RevisionUid, note UID, prescription/patient association, monotonically increasing per-note RevisionNumber, nullable content after the operation, operation Create/Update/Clear, trusted actor/time, RequestCorrelationId and linked AuditEventUid. Append only. Previous content is the preceding revision; create-before is absent, clear-after is NULL. Retain original revisions indefinitely under existing governed clinical retention until separately approved retention procedures apply; no invented year count, hard delete or generic archive/export. Store content only here and in current protected record. No new cryptography framework; preserve existing database/backup protection and restrict SQL access to these tables via affected procedures. Privileged DBA/backup governance remains a deployment qualification.

Every explicit private edit/clear takes `UPDLOCK,HOLDLOCK` on the scoped parent in a transaction, validates reviewed eight-byte parent token and Draft/author, then updates the parent metadata to advance its RowVersion, updates protected state, appends revision and inserts audit metadata. Parent ordinary update and note update in one request share **one transaction and one parent version advance**. Omitted private field leaves note/revisions untouched. A note-only save also advances parent token and has mandatory metadata audit for the parent update. Return current parent token through ordinary response; client obtains content only via protected detail. No additional note token is needed for missing/first note, ordinary edits, or finalize races.

Both finalize paths already lock the parent. Retain that serialization; a note writer winning first invalidates the finalizer's reviewed token, while a finalizer winning first makes the note writer fail Draft/version checks. Parent lock also covers first-note insertion and absent-note state. Lock parent before protected rows consistently. Cancelling/superseding never changes protected text/revisions. Failure of any parent/note/revision/audit/artifact work rolls back the entire mutation. Do not claim failed SQL writes consume no database-wide rowversion counter values; assert stored row/token are unchanged after rollback.
