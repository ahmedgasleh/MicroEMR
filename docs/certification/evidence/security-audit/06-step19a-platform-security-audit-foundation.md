# Step 19A dedicated platform security-audit foundation

## Decision and scope

Step 19 stopped because no governed central persistence contract existed for `MissingPermission`. The first Step 19A design then found that `dbo.PlatformAuditEvent` could not be safely extended: active administrative procedures use positional `INSERT dbo.PlatformAuditEvent VALUES (...)`, so adding even nullable columns would break those callers or require broad procedure rewrites.

The revised design therefore creates independent `dbo.PlatformSecurityAuditEvent` storage. The three semantic streams remain separate:

- successful clinical reads and mutations use tenant clinical audit;
- platform administrative actions continue using `PlatformAuditEvent`;
- security denials use `PlatformSecurityAuditEvent`.

Step 19A provides persistence only. Authorization handlers, controllers, responses, tenant selection, patient ownership, UI, successful-read auditing, and mutation auditing are unchanged.

## Migration and schema

Additive platform migration `014_platform_security_denial_audit.sql` creates the security table with:

| Field | Contract |
|---|---|
| `SecurityAuditEventUid` | Database-generated GUID primary key |
| `EventType` | `SecurityAccessDenied` only |
| `Outcome` | `Denied` only |
| `DenialReason` | `MissingPermission` only |
| `ActorSubject` | Required opaque authenticated subject, `NVARCHAR(450)` |
| `ClinicalUserId` | Nullable positive `BIGINT`; never inferred |
| `TargetTenantUid` | Nullable trusted/resolved tenant GUID |
| `Capability` / `RequiredPermission` | One of six controlled pairs |
| `SourceApplication` | `MicroEMR.Api` or `MicroEMR.Web` |
| `RequestCorrelationId` | Nullable trace-style string, `NVARCHAR(128)` |
| `OccurredAtUtc` | Database UTC timestamp |

No patient/resource identity, requested tenant, IP address, user-agent, URL, query string, request body, token, content, or arbitrary details field is present. Future denial slices require reviewed additive evolution.

## Capability and permission mapping

| Capability | Required permission |
|---|---|
| `PatientChartView` | `Patients.View` |
| `EncounterView` | `Encounters.View` |
| `PatientDocumentView` | `Documents.View` |
| `PatientFileDownload` | `Documents.View` |
| `AppointmentReportRun` | `Reports.View` |
| `AppointmentReportExport` | `Reports.Export` |

These values match the current application `PermissionKeys` and controller policies. Both the table constraint and stored procedure reject unknown or mismatched pairs.

## Identity and correlation

`ActorSubject` is the authoritative opaque OIDC subject and is not parsed into a clinical identifier. `ClinicalUserId` is optional and may be supplied only when already safely resolved; SQL performs no clinical lookup. `TargetTenantUid` is optional and accepts only trusted context from the future server caller; there is no requested/untrusted tenant field or cross-database lookup.

`RequestCorrelationId` accepts bounded ASP.NET-style string identifiers rather than forcing them into GUID form. Event identity and time are generated by SQL Server.

## Procedure and least privilege

`dbo.PlatformSecurityAudit_RecordMissingPermission` accepts actor, optional clinical user, optional trusted tenant, controlled capability and permission, controlled source, and optional correlation. It internally fixes event type, outcome, denial reason, event UID, and UTC time. It inserts exactly one security row and performs no update, delete, clinical lookup, administrative audit write, or business mutation.

The migration does not guess a deployment principal because none is defined in the repository. Deployment must grant that configured application principal `EXECUTE` on this procedure only. SQL Server ownership chaining then permits the procedure insert without direct table `INSERT`, `UPDATE`, or `DELETE` grants.

`IPlatformSecurityAuditRepository.RecordMissingPermissionAsync` and `SqlPlatformSecurityAuditRepository` form the smallest Step 19B-ready abstraction. The SQL repository calls only the stored procedure and lets persistence failures propagate. It is registered with platform infrastructure but is not wired to authorization.

## Index strategy

The table has investigation-focused indexes for UTC event order, trusted tenant plus time, actor plus time, and non-null request correlation. No speculative patient/resource or future-denial indexes exist.

## Tests and migration safety

Focused contract tests verify schema governance, null identity support, all approved pairs, rejection guards, fixed procedure semantics, exactly one insert, no update/delete behavior, bounded correlation, absence of clinical-content fields, stored-procedure-only repository access, no authorization wiring, and investigation indexes. They also verify that migration 014 does not alter `PlatformAuditEvent` or redefine administrative procedures.

All platform migrations 001 through 013 remain byte-for-byte unchanged and 014 is unique. Tenant migrations remain unchanged through 0046. Representative existing platform administration tests provide regression coverage for the untouched administrative stream.

Actual `013 -> 014` execution and fresh provisioning require a configured disposable SQL Server platform database. Until those executions are retained, they remain runtime evidence tasks rather than claimed results.

## Step 19B readiness

Step 19B can wire centralized `MissingPermission` authorization auditing for the six governed capabilities without another database migration. It must preserve existing denial behavior, emit one event per final authorization result, avoid patient/resource enrichment, and operationally surface persistence failures without granting access.
