## 3. Existing functionality and actual workflow

## 4. Clinical semantics and bounded decisions

These are proposed engineering contracts, not invented dictionary meanings. Unresolved authoritative semantics are separated in section 9.

1. **Administration versus refusal:** require an explicit outcome choice for the new editor. A refused vaccine can be recorded without an administration date, administrator, administered dose or lot. A vaccine name/history entry alone proves neither administration nor refusal. Existing Completed records preserve the explicit historical workflow classification; do not bulk populate a new refused=false value from record existence. EnteredInError remains terminal retained lifecycle, independent of the underlying administration/refusal information.
2. **Refusal date:** proposed meaning is the clinician-recorded date of the refusal decision/event, not entry time, an intended appointment or an administration. Year-only/month precision and unknown must work. If the applicable specification assigns a different meaning, resolve it before enabling refusal entry. No automatic date copying or mandatory exact day.
3. **Suggested minimal representation:** nullable `Refused BIT` plus a new `Refused` status alongside existing Completed/EnteredInError, with explicit consistency constraints. New explicit administered saves record false/Completed; new refused saves true/Refused. Legacy Completed or EnteredInError rows may retain NULL indicator. Active Refused requires true; Completed must not allow true; terminal rows preserve the indicator/content they had. This reuses the existing workflow without adding a second clinical source. Status Refused is an engineering label, not an asserted CT-020 value.
4. **Unknown/negative:** NULL indicator displays Not recorded, not No. False alone is not evidence of administration; completed eligibility additionally requires the existing Completed state and no contradictory fields. No unspecified/non-administration catch-all status, vaccination coverage inference or negative patient-wide assertion is introduced. Missing fields do not make historical records invalid.
5. **Outcome edits:** an explicit conversion between administration and refusal, if approved for the new editor, must reconcile incompatible fields through a deliberate, version-protected audited edit. Do not silently clear old administration data by toggling controls. If reconciliation cannot be made explicit, retain the existing record via entered-in-error and create a distinct corrected record; no automatic conversion or reopening terminal records. This policy needs agreement before refusal UI ships.
6. **Source on refusals:** ClinicAdministered is inappropriate for a non-administration event. Minimum proposed change is nullable SourceType for refused records and outcome-aware relaxation of the clinic-administrator constraint; keep existing source rules for administrations and existing terminal content. Do not invent a HistoricalExternal provenance merely to satisfy a constraint, or treat source as outcome/type. New refusal provenance vocabularies/integration are outside scope.
7. **DIN/manufacturer/type:** record supplied product identity/manufacturer independently from vaccine text and clinical CT-020 type. A product may be unidentified, particularly in a refusal. Support DIN without requiring it on every event or inventing an identifier. Validate a supplied identifier against the retained applicable DIN contract when available; preserve string/leading zeroes. No unverified numeric format, product-to-type mapping, manufacturer derivation or CT-020 vocabulary is asserted by this assessment.
8. **Dose:** DoseNumber remains an ordinal. Proposed numeric amount must be positive if supplied, bounded to the selected decimal storage without truncation or rounding; no zero-dose encoding of refusal. Proposed storage `DECIMAL(18,6)` and unit `NVARCHAR(100)` are engineering choices, subject to authoritative format confirmation. Both missing is valid unknown. For new amount input require a unit; a unit alone may be retained with unknown amount, explicitly labelled. No mandatory paired known values on legacy records, inferred mL, unit conversion or clinical dose-range rule. Refusal must not be presented as an administered amount; intended dose requires a separate future specification if needed.
9. **Dates:** reuse Application `PatientClinicalHistory/HistoryClinicalFields.cs`'s `ClinicalPartialDate` and the existing SQL date-parts function introduced by 0078/reused by 0079. Unknown = all parts NULL; YYYY, YYYY-MM and valid YYYY-MM-DD supported. Parent parts required, real calendar dates checked, full dates never timezone-shifted. Internal earliest/latest bounds are validation/sorting aids, never stored or displayed as clinical dates. Retain current no-future-administration behavior using interval validation: reject only a date whose earliest possible day is after today; an overlapping current year/month is not a fabricated future event. Future refusal-date restriction is a qualified design decision, not a new mandatory rule.
10. **Legacy compatibility:** do not rewrite old clinical rows or tokens to populate new fields. Old exact AdministrationDate reads as day precision when parts absent. Partial dates leave exact DATE NULL. Explicit administered status with unknown date must not fabricate one; the narrow old client's exact-date path remains accepted. Terminal rows remain readable/immutable, including older audit formats. New optional fields omitted by old clients must survive edits.
