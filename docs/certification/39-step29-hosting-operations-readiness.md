# Step 29 — Hosting and operations readiness

## Purpose and evidence boundary

This review packages repository evidence relevant to OntarioMD Hosting 1.3 and related Privacy & Security expectations. It is an operational-readiness assessment, not a claim of certification conformance. The repository identifies Hosting 1.3 and Privacy & Security 2.1 as applicable Stage 3 material, but does not contain their detailed clauses, substantiation reference sheet, or evidence rubric. Exact requirement mapping therefore remains **NEEDS SPECIFICATION INTERPRETATION** until the authoritative packages are obtained.

No production deployment environment, cloud account, IIS configuration, certificate inventory, secret vault, database grants, backup console, monitoring service, incident system, or operational records were available in the repository. Controls that depend on those systems are not inferred from application code.

Status vocabulary:

- **IMPLEMENTED AND VERIFIED** — present in source and supported by repository tests or directly inspectable configuration; production operation may still need separate evidence.
- **IMPLEMENTED — NEEDS EVIDENCE PACKAGING** — a suitable product boundary exists, but deployed configuration or runtime evidence is absent.
- **OPERATIONAL PROCEDURE REQUIRED** — closure principally requires an approved owner, runbook, execution record, and review.
- **MISSING** — no sufficient product or hosting-infrastructure capability/evidence was found.
- **NEEDS SPECIFICATION INTERPRETATION** — the exact normative requirement or acceptance evidence is unavailable.

## Current architecture and deployment boundary

The solution separates Auth, Web, API, Application/Core, and Infrastructure concerns. Platform/authentication data is separate from each tenant's clinical database. Runtime tenant selection requires an authenticated tenant claim, active membership, an active platform assignment, an indirect connection-string reference, a matching initial catalog, and a database identity check. DatabaseTool provides a separately enabled administrative provisioning boundary with manifest/hash tracking and serialized, transactional schema application.

The repository contains only development-oriented `appsettings` and launch profiles. It contains no production topology diagram, IIS `web.config`, reverse-proxy configuration, container/IaC definition, deployment pipeline, production environment overlay, hosting-provider record, Canadian residency evidence, network diagram, firewall rules, load-balancer configuration, or service-account manifest. Consequently IIS/reverse-proxy termination, forwarded-header handling, end-to-end HTTPS, availability, scaling, geographic residency, and least-privilege runtime identities are not verified.

Auth applies production HSTS and HTTPS redirection; API applies HTTPS redirection and requires HTTPS OIDC metadata. Web has no in-process HSTS or HTTPS-redirection middleware. That may be acceptable behind a correctly configured HTTPS reverse proxy, but the absent topology and proxy evidence prevent that conclusion. API Swagger is enabled without an environment guard, so production exposure must be explicitly restricted or justified. Auth currently registers OpenIddict development encryption and signing certificates; a production signing/encryption certificate loading and rotation mechanism is an implementation/configuration gap.

The controlled tenant SQL environment has a documented TLS failure even with certificate trust bypass: SQL Server 2019 RTM reports that encryption is required but unsupported by the machine. A temporary unencrypted diagnostic connection worked and was removed. Production must not use that workaround. The documented corrective boundary is server patching, TLS 1.2/cipher enablement, and a trusted hostname-matching certificate.

## Closure-path summary

For the 20 explicitly requested control areas, **10 are evidence/procedure closure candidates** using existing product boundaries: production secret storage, OIDC secret rotation, tenant DB connection security, restore testing, tenant DB provisioning, deployment, rollback, patching, secure environment configuration, and certificate-renewal procedure. This does not mean those controls currently pass; several depend on prerequisite infrastructure.

The other **10 require a product or hosting-infrastructure capability/configuration before evidence can close them**: production TLS, backup, disaster recovery, patient-file backup/storage, operational logging, audit retention, monitoring, broader health-check coverage, least-privilege deployed service identities, and data disposal. Incident response and sensitive-log redaction are related Privacy & Security controls outside that numbered 20; they also remain open.

## Required evidence package

An eventual Hosting 1.3 package should contain authoritative clause-to-evidence mapping; approved topology/data-flow and residency diagrams; IIS/proxy/firewall/TLS configuration; certificate inventory and renewal record; secret-vault and rotation evidence; redacted connection configuration and SQL/IAM grants; provisioning and isolation results; backup policies/job records and coordinated restore results; approved RPO/RTO and DR exercise; file-store durability/backup/reconciliation proof; logging/redaction/retention/access records; monitoring dashboards and alert exercises; health semantics and outage drills; versioned deployment/rollback/patch records; service-identity reviews; incident tabletop evidence; and approved retention, legal-hold, and disposal records.

Screenshots and exports must be redacted. They must not include passwords, client secrets, connection strings, tokens, certificate private keys, patient data, or unbounded production log content.

## Concrete defects and risks reported without remediation

This documentation-only step changes no production code. The following concrete risks require separate authorization and implementation/configuration work:

1. The controlled SQL Server 2019 RTM endpoint cannot establish the required encrypted connection and must be patched/configured; disabling encryption is prohibited for production.
2. Auth uses OpenIddict development signing and encryption certificates; a production certificate mechanism and lifecycle are absent.
3. Web contains no in-process HTTPS redirection/HSTS and no proxy topology evidence establishes equivalent enforcement.
4. API Swagger is unconditionally exposed by application startup and needs a production exposure decision/control.
5. Only API platform-database health is covered; Auth, Web, tenant database, OIDC, and file-storage readiness are not.
6. The only patient-file implementation is local filesystem storage without a production durability, encryption, malware-scanning, backup, restore, or retention control.

## One recommended next hosting-readiness action

**Remediate the controlled SQL Server TLS stack and capture a successful encrypted, hostname-validated tenant connection evidence record.** This is the highest-priority bounded action because a known active transport failure prevents credible tenant-database security evidence and must not be bypassed with an unencrypted connection.

After that action is reviewed, the broader operational evidence program can be sequenced separately; Step 29 does not authorize those changes.
